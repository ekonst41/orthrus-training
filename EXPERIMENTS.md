# Эксперименты с циклом декодирования

## Вопрос

Цикл Orthrus из статьи — два прохода: диффузионный вид предлагает блок из K−1 = 31 черновых токенов,
AR-вид проверяет его и оставляет совпавший префикс плюс свой следующий токен («бонус»). Всё, что в
блоке после первой ошибки, выбрасывается. Гипотеза: в этом хвосте часто есть верные токены — ошибка
бывает локальной (заменённое слово) или хвост просто сдвинут на позицию (черновик пропустил или
вставил токен). Тогда третий проход — AR-проверка оставшегося хвоста после бонуса — даст ещё
несколько токенов. Поднимет ли это TPF, если честно считать третий проход?

TPF = новые токены / все прямые проходы (префилл, диффузия, проверки, проверки хвоста).
Хвостовой проход добавляет «принятое из хвоста + 1 AR-токен», поэтому он повышает TPF, только если
в среднем даёт больше токенов, чем текущий TPF (у официальных моделей 1.7B/4B это ~3–6).

## Стратегии (`orthrus/decoding.py`)

| Стратегия | Цикл | Проходов на цикл |
|---|---|---|
| `base` | черновик → проверка (статья; совпадает с `OrthrusLM.diffusion_generate`) | 2 |
| `tail` | черновик → проверка → проверка хвоста после бонуса | 2 или 3 |
| `reuse` | черновик → проверка, где проверка следующего блока заодно проверяет хвост предыдущего | 2 |

Гипотеза хвоста со сдвигом s после отклонения черновика `d[a]` (бонус встаёт на его место)
продолжает бонус токенами `d[a+1−s:]`:

- `s = 0` — замена: бонус заменил `d[a]`, дальше черновик верен;
- `s = +1` — черновик пропустил токен: бонус вставляется, дальше идёт `d[a]`;
- `s = −j` — черновик вставил j лишних токенов: `d[a+j]` должен совпасть с бонусом.

Несколько гипотез проверяются одним проходом с древовидной маской внимания (каждая видит префикс,
бонус и свои предыдущие токены); остаётся та, у которой принято больше токенов. Сохраняются только
токены, которые предсказал AR-вид, поэтому жадный вывод любой стратегии равен обычному AR.

Параметры `tail`: `shifts` — набор сдвигов; `min_tail` — проверять хвост, только если в гипотезе
не меньше стольких токенов; `min_expected` — только если ожидаемый выход прохода
`1 + Σ_j Π_{i≤j} p_i` (p — вероятности черновых токенов у диффузионного вида) не меньше порога;
`max_tail_passes` — сколько раз подряд проверять остаток хвоста. `oracle_min_tokens` — «идеальный
затвор», заглядывающий в результат: только для симуляции, это потолок для любого реального правила.

## Постановка

- **Модели** — все официальные чекпоинты статьи: `chiennv/Orthrus-Qwen3-1.7B@7dc9735`,
  `chiennv/Orthrus-Qwen3-4B@cd93cb3`, `chiennv/Orthrus-Qwen3-8B@977a617` (K = 32, токен маски
  151669, EOS 151645), загружаются нашим `OrthrusLM` (имена тензоров совпадают; у 1.7B и 4B
  `lm_head` связан с эмбеддингами, у 8B — отдельный).
- **Промпты** — замороженный набор `decode-v1` (sha256 `16f6056c…`, закреплён в конфигах;
  `experiments/prompts/decode-v1.jsonl` в бакете, метаданные — `decode-v1.json`): GSM8K, MATH-500,
  HumanEval, MBPP с закреплёнными ревизиями (zero-shot, вопрос как реплика пользователя, как в
  `orthrus.evaluate`) и chat — отложенные промпты Nemotron v2 из нашей генерации данных (официальные
  модели могли видеть их при обучении: абсолютный TPF это завышает, сравнение стратегий — нет).
  Порядок внутри набора — по sha256(seed:набор:id), чётные ранги — dev, нечётные — test.
  Токенизаторы всех трёх моделей дают для всех промптов ровно записанные ids (проверяется при
  загрузке каждой модели).
- **Бюджет** — не больше ~1 GPU-часа на весь эксперимент: одно задание на три модели
  (`jobs/decode-tail.yaml`, `configs/decode/tail-v1.yaml`). Работа идёт раундами: раунд r — промпт
  r каждого из 5 наборов на модели, у которой раундов меньше всего, и выгружается сразу. Поэтому в
  любой момент данные сбалансированы по моделям и наборам, а отчёт можно строить, пока задание идёт.
  Новые раунды не начинаются после `decode.max_minutes` = 45 мин. Веса качаются в фоне по одной
  модели: следующая — только когда предыдущая уже в памяти, а её файлы удалены (на диске задания
  ~34 ГБ, меньше окружения и трёх чекпоинтов). Все три fp32-модели (~68 ГБ) держатся на A100 80 ГБ.
- **На GPU по каждому промпту** — только `base` (эталонный выход) и таблица черновиков; все
  стратегии и политики считаются по ним точным воспроизведением на CPU. В проверочном раунде 0
  `tail-tree` и `reuse-tree` дополнительно декодируются по-настоящему, а один промпт — обычным AR.
- **Декодирование** — жадное, batch 1, без thinking, до 512 новых токенов, **fp32 без TF32**.
  В bf16 почти-ничьи логитов AR решает округление, и разные стратегии (разная нарезка проверок)
  расходятся в токенах. В fp32 любая стратегия выдаёт ровно AR-ответ, поэтому сравнение парное:
  одни и те же токены, разное число проходов. TPF — счётная величина и от dtype не зависит;
  время в fp32 не показательно для bf16-развёртывания.
- **Воспроизведение без модели.** При жадном декодировании исход любой проверки определяется
  эталонным ответом: токен принимается, если он равен следующему токену ответа. Поэтому для каждого
  промпта считается таблица черновиков — что предложил бы диффузионный вид в каждой позиции ответа
  (`decoding.draft_table`: один AR-проход по ответу и пачки по 32 блока с маской обучения), и любая
  стратегия проигрывается на CPU точно (`decoding.OracleBackend`). Это даёт перебор сотен политик
  без GPU.

## Проверки достоверности

`base` проверяется на каждом промпте, `tail-tree` и `reuse-tree` — на промптах проверочного раунда:

| Поле записи | Что проверяет |
|---|---|
| `match_base` | вывод стратегии совпал с выводом `base` токен в токен |
| `match_ar` | вывод совпал с обычным жадным AR (один промпт на модель) |
| `draft_mismatch` | черновики, которые стратегия реально получила, совпали с таблицей черновиков |
| `sim_match` | проигрыш стратегии по таблице дал те же проходы, принятия и хвосты, что реальный запуск |

Принятие заканчивается на принятом EOS: токены после конца ответа не считаются, даже если AR-вид с
ними согласен (найдено пилотом: иначе счётчик последнего цикла зависел от «мусора» после EOS, а в
древовидной проверке мог зависеть и выбор ветки; выход и число проходов от этого не менялись).

Пилот (задание `bt1mhd12pctpdeb30f6i`, коммит `9cc513e`, 1.7B и 4B, по 2 промпта на набор, все пять
стратегий декодировались по-настоящему, до 1024 токенов, ~25 GPU-минут) подтвердил на A100:
все выходы равны AR и друг другу, черновики совпали с таблицей на всех 7 946 посещённых якорях, а
после исправления учёта EOS воспроизведение совпало со всеми 100 реальными декодированиями.

`decode_report` выводит доли проверок в разделе «Checks» отчёта. Код проверен тестами на CPU
(`tests/test_decoding.py`, `tests/test_decode_exp.py`): `base` совпадает с официальным циклом по
токенам и проходам, древовидная проверка равна отдельным цепочкам (логиты и кэш), на «сценарных»
черновиках с заменой/пропуском/вставкой хвост чинится ровно нужным сдвигом, проигрыш равен
реальному запуску, таблица черновиков равна черновикам декодирования.

Статистика: TPF по набору — отношение сумм по промптам; «avg» — среднее по наборам, как в Таблице 1
статьи; 95% доверительные интервалы — бутстреп по промптам (2000 выборок, seed 0, наборы
ресэмплируются отдельно); разности с `base` парные. «Идеальный затвор» — лучшая по порогу k политика
«проверять хвост (все сдвиги), только если проход сохранит ≥ k токенов» с подглядыванием в
результат: потолок для любого реального правила включения третьего прохода. Политики из перебора
ранжируются по dev, лучшая отчитывается на test.

## Запуск

```bash
# один раз: набор промптов (сделано; печатает sha256 для decode.prompt_set_sha256)
python -m orthrus.decode_exp --config configs/decode/tail-v1.yaml --build-prompts

# эксперимент: три модели, ~1 GPU-час; перезапуск продолжает с недостающих раундов
python scripts/ds.py run jobs/decode-tail.yaml --max-minutes 62 --retry-minutes 120

# анализ на любой машине (CPU), в том числе пока задание идёт
python -m orthrus.decode_report --config configs/decode/tail-v1.yaml [--grid small|full|none]
```

Лог задания после каждого раунда печатает воспроизведённый TPF всех стратегий по моделям. Локально
переменные из `.env` нужно экспортировать (`set -a; source .env; set +a` в bash).

Раскладка в бакете (`experiments/decode-tail-v1/`):

| Файл | Содержимое |
|---|---|
| `run.json` | конфиг, коммит, версии, GPU, sha256 набора промптов, стратегии, модели, по сегменту на задание |
| `<модель>/model.json` | репозиторий, ревизия, коммит, EOS, K, токен маски, dtype |
| `<модель>/round-NNNN.jsonl` | строка на реальное декодирование: токены, проходы и входные токены по видам, время, принятия по циклам, хвостовые проходы, проверки; выгружается вторым — отмечает завершённый раунд |
| `<модель>/round-NNNN.npz` | эталонные ответы, таблицы черновиков и вероятностей (для воспроизведения) |
| `analysis/` (локально) | `report.md`, `summary.json`, `policy_grid.csv` от `decode_report` |
