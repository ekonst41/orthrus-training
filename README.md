# Orthrus training for Qwen3

Воспроизведение обучения [Orthrus](https://arxiv.org/abs/2605.12825): к замороженной Qwen3 добавляется
обучаемый диффузионный «вид» внимания, который предлагает K токенов за один проход, а сама модель
проверяет их за второй проход. Генерация остаётся без потерь, но идёт в несколько раз быстрее.
Целевой запуск — Qwen3-0.6B на одной A100 80 ГБ в Yandex DataSphere; код работает и на любом
Linux-сервере с CUDA.

## Конвейер

| Шаг | Команда | Результат в HF-бакете | Время на A100 |
|---|---|---|---|
| 1. Данные | `python -m orthrus.datagen --config configs/qwen3-0.6b.yaml` | `data/<dataset>/raw/shard-*.parquet`, `prompts.parquet`, `eval_prompts.jsonl`, `manifest.json`, `datagen_metrics.jsonl` | ~10.5–11 ч |
| 2. Обучение | `python -m orthrus.train --config configs/qwen3-0.6b.yaml` | `runs/<run>/checkpoints/`, `final/`, `train_metrics.jsonl`, `run.json`, `logs/` | ~29 ч |
| 3. Оценка | `python -m orthrus.evaluate --config configs/qwen3-0.6b.yaml eval.dtype=float32 eval.max_new_tokens=512` | `runs/<run>/eval-<модель>-<N>-<dtype>.json` | ~45 мин |
| Просмотр | `python -m orthrus.report --config configs/qwen3-0.6b.yaml [--show]` | — (читает бакет) | — |
| Инференс | `python -m orthrus.generate --config configs/qwen3-0.6b.yaml --prompt "..."` | — | — |

Время — оценка для полного рецепта (525 тыс. диалогов, 2 эпохи), стоимость g2.1 ≈ 543 ₽/ч.
Каждый шаг можно прервать и перезапустить: генерация продолжается с первого недостающего шарда,
обучение — с последнего чекпоинта, с теми же данными и якорями, что и без перерыва (проверяется
тестом). Любой параметр переопределяется из командной строки: `train.max_steps=20`.

В DataSphere те же шаги запускаются заданиями (окружение — в [DEVELOPMENT.md](DEVELOPMENT.md)):

```bash
python scripts/ds.py run jobs/smoke.yaml --max-minutes 60          # весь конвейер на крошечных данных
python scripts/ds.py run jobs/datagen.yaml --max-minutes 1400 --retry-minutes 120
python scripts/ds.py run jobs/train.yaml --max-minutes 1400 --retry-minutes 120  # повторять до конца
python scripts/ds.py run jobs/eval.yaml --max-minutes 120          # 32 промпта на набор, fp32
```

Одно задание идёт не дольше 22 ч (`max_hours`) и само сохраняется перед концом; следующий запуск
того же задания продолжает работу. `--max-minutes` — внешний предохранитель: DataSphere сама
длительность не ограничивает.

## Наблюдение и управление

- **Метрики и состояние** — `python -m orthrus.report --config configs/qwen3-0.6b.yaml`: сегменты
  запуска (задание, коммит, шаги, часы, стоимость), текущий шаг и ETA, кривая обучения, оценки по
  ходу обучения, итоговые оценки и ход генерации данных. `--show` загружает историю метрик в
  локальный дашборд Trackio (графики всех метрик по шагам, сглаживание); `--run a,b` сравнивает
  запуски. Метрики в бакете обновляются при каждой записи лога (`train.log_every`).
- **Задание** — прогресс-бар на странице задания в DataSphere; `python scripts/ds.py attach <id>` —
  поток логов; если поток CLI остановился (бывает после обновления токена `yc`), состояние видно в
  `python scripts/ds.py get <id>`, а вывод — в `.ds_logs/<время>-<задание>/stdout.txt`.
- **Остановка** — `python scripts/ds.py stop runs/<run>` (или `data/<dataset>` для генерации)
  кладёт в бакет файл `STOP`: обучение на ближайшей записи лога сохраняет и выгружает чекпоинт и
  завершается, генерация — после текущего шарда; следующий запуск продолжает работу.
  `ds.py cancel <id>` снимает задание за ~20 с без сохранения (DataSphere не выдерживает
  `graceful-shutdown`, проверено `jobs/probe-signal.yaml`), теряются шаги после последнего
  чекпоинта (до `train.save_every`, ~45 мин). Если шаги не идут `train.stall_minutes` минут
  (генерация — `datagen.stall_minutes`), процесс сам завершается с кодом 3, чтобы зависание не
  оплачивалось до таймаута.
- **Новый запуск или продолжение** — запуск определяется `run_name`: тот же `run_name`
  продолжает обучение, а при изменённом рецепте (модель, данные, оптимизация) отказывается
  продолжать; для нового эксперимента задайте новый `run_name`.

Логируются (`runs/<run>/train_metrics.jsonl`, одна строка на запись):

| Префикс | Что |
|---|---|
| `train/` | `loss` (KL), `top1_agreement`, `agree_k{1,2,4,8,16,31}` по позициям блока, `acceptance_proxy`, `grad_norm`, `lr`, `epoch`, `valid_anchors`, `skipped_steps` |
| `perf/` | `seconds_per_step` (без времени оценок и сохранений), `input_tokens_per_second`, `eta_hours`, `max_memory_gb`, `memory_reserved_gb`, `gpu_util`, `gpu_power_w` |
| `eval/` | KL и согласие на 256 отложенных строках (каждые `train.eval_every` шагов) |
| `generate/` | настоящая диффузионная генерация отложенных промптов (поровну math/code/chat): `tpf`, `acceptance_length`, `tokens_per_cycle`, `tokens_per_second` и они же по доменам (`generate/math/tpf`) |

## Данные

Промпты — Nemotron-Post-Training-Dataset-v2 (math, code, chat 1:1:1), ответы — сама Qwen3-0.6B
жадно, без thinking, до 2048 токенов (как в примере официального README). Отбор промптов
детерминирован (хэш `seed:uuid`) и кэшируется в `prompts.parquet`: перезапуск отвечает на те же
промпты в том же порядке. Ревизии модели и датасета закреплены в конфиге (`model.revision`,
`datagen.source_revision`); обучение проверяет, что учитель — та же ревизия, что писала данные.

Отличие от статьи по объёму: статья обучает на 600 тыс. примеров (0.96 млрд токенов, 471 952
упакованные строки), а code в Nemotron v2 — 175 тыс. промптов, поэтому при строгом 1:1:1 у нас
525 тыс. диалогов. Замер генерации (`jobs/genbench.yaml`, первые 700 промптов каждого домена):
средний ответ 688 токенов (chat 450, code 620, math 990; 7% обрываются на 2048), средний промпт
304 токена — итого ~0.52 млрд токенов, ~254 тыс. строк.

Генерация упирается в чтение KV-кэша (112 КБ на токен), поэтому скорость не зависит от размера
батча, но падает по мере удлинения контекстов: 12.3 тыс. токенов/с в начале, ~9.5–10 тыс. в
установившемся режиме, когда в батче копятся длинные ответы (в среднем за замер 10.5 тыс.;
полная генерация — 361 млн токенов ответов, ~10–10.6 ч плюс ~0.5 ч на подготовку). 256 и 512 одновременных последовательностей дают
одно и то же, вытеснений нет.
Speculative decoding в vLLM не ускоряет: `ngram_gpu` 0.99× (принимает 0.6–0.8 токена за шаг),
`ngram` на CPU 0.90× (принимает 1.6 токена, но предложения для 512 запросов считаются на CPU),
`suffix` (Arctic Inference) не помещается в память при 24 черновых токенах и тоже работает на CPU;
поэтому он выключен (`datagen.speculative: {}`). Детокенизация отключена (нужны только id), на
скорость это не влияет. Важно: жадная генерация Qwen3-0.6B в bf16
не воспроизводится бит в бит — от состава батча зависят почти-ничьи логитов, и два одинаковых
запуска vLLM совпадают лишь в ~17% ответов (расходясь в среднем к 160-му токену). Поэтому набор
данных генерируется один раз и хранится; «ответ модели» определён с точностью до этого шума.

Упаковка — как в официальном коде: диалоги перемешиваются и склеиваются в строки по 2048 токенов
без масок между документами.

## Рецепт и откуда взято каждое решение

Приоритет источников: статья → [официальный код](https://github.com/chiennv2000/orthrus) →
[Zarya-Orthrus](https://github.com/ai-forever/Zarya-Orthrus). Значения по умолчанию — в
`orthrus/config.py`, у каждого указан источник.

| Что | Значение | Источник |
|---|---|---|
| Функция потерь | прямая KL(p_AR ‖ p_diff) по замаскированным позициям | статья |
| Блок, блоков на строку, длина строки | K = 32, 256, 2048 (упаковка) | статья |
| Эпохи, LR, расписание, clip | 2, 2e-4, cosine + 5% warmup, 1.0 | статья |
| Глобальный батч | 128 последовательностей (micro 4 × накопление 32) | статья |
| Данные | Nemotron-Post-Training-v2 math:code:chat 1:1:1, ответы самой модели | статья |
| Генерация ответов | жадно, без thinking, до 2048 новых токенов | офиц. README |
| Обучаемые веса | q/k/v/o_proj_diff + q/k_norm_diff, старт с копии AR-весов | офиц. код, офиц. чекпоинт |
| Маска внимания | AR-ключи строго до якоря + двунаправленно внутри блока | статья, офиц. код |
| Якоря | позиции ответа ассистента, без повторов; цель — токены ассистента | офиц. код |
| AdamW, нижний предел LR | betas (0.9, 0.95), wd 0; 10% от пика | офиц. код |
| Токен маски | `len(tokenizer)` (151669), строка эмбеддинга не меняется | офиц. чекпоинт |
| Нормировка потерь | среднее по токенам микробатча, затем по накоплению | офиц. код |
| Формат экспорта | Qwen3-конфиг + `block_size`, `mask_token_id`, `modeling_orthrus.py` | офиц. чекпоинт |

Отклонения, которых требует железо или которые не меняют алгоритм:
FlexAttention на Triton вместо FlashAttention-4 (его нет для A100); логиты словаря накапливаются
сразу в fp32 (без округления целей учителя до bf16); градиент KL считается вместе с потерей
(меньше памяти и вычислений, тот же результат — проверяется тестом против autograd).
Официальный код обучения (для Qwen3.5) использует cross-entropy по токенам данных вместо KL;
мы следуем статье (KL обходится лишь на 8% дороже).

## Оценка и инференс

`orthrus.evaluate` генерирует жадно с batch 1 на отложенных промптах (поровну math/code/chat) и на
промптах GSM8K, MATH-500, HumanEval, MBPP — `eval.prompts` на набор — диффузионно и обычным AR, и
считает метрики. `eval.checkpoint=step-0002000` (или `latest`) оценивает чекпоинт обучения, а не
экспорт. Задание `jobs/eval.yaml` — 32 промпта на набор, 512 новых токенов, fp32.

Определения, при которых сходятся числа статьи (Таблица 1 и Рис. 4):

- `acceptance_length` — принятых черновых токенов за цикл «диффузия + проверка», без бонусного;
- `tpf` — сгенерированных токенов на прямой проход, проходов = 1 + 2 × циклы;
- `tokens_per_cycle` — токенов на проход проверки (так считает TPF скрипт Zarya);
- `ar_match` — доля промптов, где ответ совпал с обычной жадной генерацией. В fp32 она 1.0
  (проверено); в bf16 ниже, потому что top-1 и top-2 логиты AR часто равны с точностью до шага bf16
  (`ar_divergence_logit_gap` ≈ 0) и выбор решает округление — поэтому оценка идёт в fp32;
- `speedup` — время AR-генерации / время Orthrus на тех же промптах (HF-реализация с batch 1:
  у модели 0.6B время прохода определяется накладными расходами, а не вычислениями).

Инференс: `python -m orthrus.generate --config configs/qwen3-0.6b.yaml --prompt "..."` печатает ответ
потоком и статистику (токенов за цикл, TPF, токены/с; `--compare-ar` — время AR и совпадение);
без `--prompt` — диалог в терминале; `--model DIR` — любой экспорт, в том числе официальные
`chiennv/Orthrus-Qwen3-*`. Экспорт — обычная HF-модель:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("runs/runs/<run>/final", trust_remote_code=True)
tokenizer = AutoTokenizer.from_pretrained("runs/runs/<run>/final")
ids = tokenizer.apply_chat_template(
    [{"role": "system", "content": ""}, {"role": "user", "content": "2+2?"}],
    add_generation_prompt=True,
    enable_thinking=False,
    return_tensors="pt",
).input_ids
print(tokenizer.decode(model.generate(ids, max_new_tokens=256)[0]))  # диффузионный режим
```

## Воспроизводимость

- Порядок данных: перемешивание диалогов (`data.seed`), порядок батчей (`train.seed`, эпоха),
  якоря — свой генератор на каждый (seed, эпоха, micro-batch); продолжение после перерыва даёт
  бит-в-бит те же веса (тест).
- Чекпоинт: обучаемые веса, AdamW, scheduler, шаг и рецепт; запись атомарна, в бакете файл
  `trainer_state.json` выгружается последним и помечает полный чекпоинт.
- `run.json`: конфиг, коммит (с пометкой `-dirty`, `ds.py` об этом предупреждает), sha lock-файла,
  версии torch/triton/transformers/vLLM/CUDA, GPU и по сегменту на каждое задание (коммит,
  задание, шаги, часы, причина остановки).
- Закреплены ревизии модели и датасета; манифест данных хранит ревизии и параметры генерации.
- Не бит-в-бит: генерация данных vLLM (см. «Данные»); ядра GPU в обучении детерминированы для
  одинаковых форм, но это проверено только на CPU.

## Скорость обучения

Замер `python -m orthrus.bench` на A100 80GB: прямой + обратный проход одного micro-batch
(4 строки × 2048, 256 блоков × 32), одинаковые реальные данные.

| Путь | с / micro-batch | пик памяти |
|---|---|---|
| исходный (HF-модули, KL по строке на каждую позицию) | 1.79 | 62.8 ГБ |
| + функциональные слои под `torch.compile`, общий KL | 0.98 | 38.0 ГБ |
| + пропуск dK/dV для AR-ключей | 0.83 | 38.7 ГБ |
| + KL-ядра со статическим словарём (текущий) | 0.82 | 38.7 ГБ |

Настоящее обучение: 3.3 с на шаг из 16 последовательностей вместо 7.1 (≈26 с на шаг рецепта из
128 вместо 57). Все изменения сохраняют математику: функциональный путь совпадает с модульным
(тест), пропуск dK/dV даёт бит-в-бит те же градиенты, ошибка градиента относительно fp32 у старого
и нового bf16-пути одинаковая (≈3%, косинус 0.9996).

1. **Слои как функции весов под `torch.compile`** (`objective.model_states`): RMSNorm, RoPE,
   SwiGLU, residual и FlexAttention сливаются в один граф на слой; поэлементные eager-ядра
   занимали 55% шага.
2. **Общие цели KL**: 256 блоков по 32 в строке 2048 перекрываются, одна позиция — цель ~4 блоков;
   проекция учителя на словарь считается один раз на позицию.
3. **Слитое ядро KL**: log-softmax, KL, top-1 и градиент `p_s − p_t` за 2 прохода по логитам
   вместо ~15; размер словаря статический, динамическое только число строк.
4. **Без dK/dV для AR-ключей**: ключи учителя заморожены, их градиент выбрасывался, но был почти
   всей работой dK/dV (каждый блок видит весь префикс). В маске обратного прохода списки q-блоков
   AR-ключей пусты (`objective.skip_ar_key_grads`); forward и dQ не меняются.

Проверено и не дало выигрыша: размеры чанка KL 4096/8192, параметры ядра FlexAttention
(max-autotune выбирает те же конфиги, что и по умолчанию), `ROWS_GUARANTEED_SAFE` (даёт NaN).
Micro-batch 8 быстрее на 2.5% при пике 72 ГБ (оставлен 4).

## Структура

```text
orthrus/
  modeling_orthrus.py  модель (самодостаточна: кладётся в экспорт как modeling_orthrus.py)
  objective.py         якоря, маска супервизии, быстрые проходы обоих видов, слитая KL
  train.py             цикл обучения: продолжение, рецепт, бюджет времени, STOP, оценка, экспорт
  data.py              упаковка сгенерированных диалогов в строки
  datagen.py           отбор промптов (с кэшем) и генерация ответов через vLLM
  evaluate.py          метрики скорости и паритета, бенчмарки, оценка чекпоинтов
  generate.py          инференс в терминале со статистикой декодирования
  report.py            сводка запусков и локальный дашборд Trackio
  checkpoint.py        загрузка модели, чекпоинты, экспорт
  storage.py           HF Storage Bucket
  tracking.py          JSONL-метрики, паспорт запуска, прогресс DataSphere, сторож зависаний
  bench.py, genbench.py  замеры скорости обучения и генерации данных
  config.py            конфигурация
configs/   эксперименты (qwen3-0.6b.yaml — рецепт статьи, smoke.yaml — быстрая проверка)
jobs/      задания DataSphere
scripts/   ds.py (запуск заданий), lock.py (зависимости), пробы окружения
tests/     тесты на CPU с крошечной моделью (pytest)
```
