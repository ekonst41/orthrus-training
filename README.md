# Orthrus training for Qwen3

Воспроизведение обучения [Orthrus](https://arxiv.org/abs/2605.12825): к замороженной Qwen3 добавляется
обучаемый диффузионный «вид» внимания, который предлагает K токенов за один проход, а сама модель
проверяет их за второй проход. Генерация остаётся без потерь, но идёт в несколько раз быстрее.
Целевой запуск — Qwen3-0.6B на одной A100 80 ГБ в Yandex DataSphere; код работает и на любом
Linux-сервере с CUDA.

## Конвейер

| Шаг | Команда | Результат в HF-бакете |
|---|---|---|
| 1. Данные | `python -m orthrus.datagen --config configs/qwen3-0.6b.yaml` | `data/<dataset>/raw/shard-*.parquet`, `eval_prompts.jsonl`, `manifest.json` |
| 2. Обучение | `python -m orthrus.train --config configs/qwen3-0.6b.yaml` | `runs/<run>/checkpoints/`, `final/`, метрики, `run.json` |
| 3. Оценка | `python -m orthrus.evaluate --config configs/qwen3-0.6b.yaml` | `runs/<run>/eval-<N>.json` |

Каждый шаг можно прервать и перезапустить: генерация продолжается с первого недостающего шарда,
обучение — с последнего чекпоинта, причём с теми же данными и якорями, что и без перерыва
(проверяется тестом). Любой параметр переопределяется из командной строки: `train.max_steps=20`.

В DataSphere те же шаги запускаются заданиями (окружение — в [DEVELOPMENT.md](DEVELOPMENT.md)):

```bash
python scripts/ds.py run jobs/smoke.yaml --max-minutes 60      # весь конвейер на крошечных данных
python scripts/ds.py run jobs/datagen.yaml --retry-minutes 120 # генерация датасета
python scripts/ds.py run jobs/train.yaml --retry-minutes 120   # обучение (повторять до конца)
python scripts/ds.py run jobs/eval.yaml                        # замер скорости
```

Метрики видны в дашборде Trackio (приватный HF Space из `ORTHRUS_TRACKIO_SPACE`) и в файлах
`*_metrics.jsonl`, которые лежат в бакете рядом с чекпоинтами.

## Рецепт и откуда взято каждое решение

Приоритет источников: статья → [официальный код](https://github.com/chiennv2000/orthrus) →
[Zarya-Orthrus](https://github.com/ai-forever/Zarya-Orthrus). Значения по умолчанию — в
`orthrus/config.py`, у каждого указан источник.

| Что | Значение | Источник |
|---|---|---|
| Функция потерь | прямая KL(p_AR ‖ p_diff) по замаскированным позициям | статья |
| Блок, блоков на строку, длина строки | K = 32, 256, 2048 (упаковка) | статья |
| Эпохи, LR, расписание, clip | 2, 2e-4, cosine + 5% warmup, 1.0 | статья |
| Глобальный батч | 128 последовательностей (micro × накопление) | статья |
| Данные | Nemotron-Post-Training-v2 math:code:chat 1:1:1, ответы самой модели | статья |
| Обучаемые веса | q/k/v/o_proj_diff + q/k_norm_diff, старт с копии AR-весов | офиц. код, офиц. чекпоинт |
| Маска внимания | AR-ключи строго до якоря + двунаправленно внутри блока | статья, офиц. код |
| Якоря | позиции ответа ассистента, без повторов; цель — токены ассистента | офиц. код |
| AdamW, нижний предел LR | betas (0.9, 0.95), wd 0; 10% от пика | офиц. код |
| Токен маски | `len(tokenizer)` (151669), строка эмбеддинга не меняется | офиц. чекпоинт |
| Нормировка потерь | среднее по токенам микробатча, затем по накоплению | офиц. код |
| Формат экспорта | Qwen3-конфиг + `block_size`, `mask_token_id`, `modeling_orthrus.py` | офиц. чекпоинт |

Отклонения, которых требует железо или которые не меняют алгоритм:
FlexAttention на Triton вместо FlashAttention-4 (его нет для A100); логиты словаря накапливаются
сразу в fp32 (без округления целей учителя до bf16); градиент KL считается вместе с потерей
(меньше памяти и вычислений, тот же результат — проверяется тестом против autograd).

## Метрики скорости

Определения, при которых сходятся числа статьи (Таблица 1 и Рис. 4):

- `acceptance_length` — принятых черновых токенов за цикл «диффузия + проверка», без бонусного;
- `tpf` — сгенерированных токенов на прямой проход, проходов = 1 + 2 × циклы;
- `tokens_per_cycle` — токенов на проход проверки (так считает TPF скрипт Zarya);
- `ar_match` — доля промптов, где ответ совпал с обычной жадной генерацией. В fp32
  (`eval.dtype=float32`) она равна 1.0; в bf16 ниже, потому что top-1 и top-2 логиты AR часто
  совпадают с точностью до шага bf16 (`ar_divergence_logit_gap` ≈ 0), и выбор решает округление;
- `speedup` — время AR-генерации / время Orthrus на тех же промптах.

Во время обучения дополнительно логируются совпадение top-1 с учителем по позициям блока
(`agree_k*`) и прокси длины приёмки (`acceptance_proxy`) — дешёвый ранний сигнал качества.

## Скорость обучения

Замер `python -m orthrus.bench` на A100 80GB: прямой + обратный проход одного micro-batch
(4 строки × 2048, 256 блоков × 32), одинаковые реальные данные.

| Путь | с / micro-batch | пик памяти |
|---|---|---|
| исходный (HF-модули, KL по строке на каждую позицию) | 1.79 | 62.8 ГБ |
| + функциональные слои под `torch.compile`, общий KL | 0.98 | 38.0 ГБ |
| + пропуск dK/dV для AR-ключей | 0.83 | 38.7 ГБ |
| + KL-ядра со статическим словарём (текущий) | 0.82 | 38.7 ГБ |

Настоящее обучение: 3.3 с на шаг из 16 последовательностей вместо 7.1 (≈26 с на шаг рецепта из
128 вместо 57). Все изменения сохраняют математику: функциональный путь совпадает с модульным
(тест), пропуск dK/dV даёт бит-в-бит те же градиенты, ошибка градиента относительно fp32 у старого
и нового bf16-пути одинаковая (≈3%, косинус 0.9996).

1. **Слои как функции весов под `torch.compile`** (`objective.model_states`): RMSNorm, RoPE,
   SwiGLU, residual и FlexAttention сливаются в один граф на слой; поэлементные eager-ядра
   занимали 55% шага.
2. **Общие цели KL**: 256 блоков по 32 в строке 2048 перекрываются, одна позиция — цель ~4 блоков;
   проекция учителя на словарь считается один раз на позицию.
3. **Слитое ядро KL**: log-softmax, KL, top-1 и градиент `p_s − p_t` за 2 прохода по логитам
   вместо ~15; размер словаря статический, динамическое только число строк.
4. **Без dK/dV для AR-ключей**: ключи учителя заморожены, их градиент выбрасывался, но был почти
   всей работой dK/dV (каждый блок видит весь префикс). В маске обратного прохода списки q-блоков
   AR-ключей пусты (`objective.skip_ar_key_grads`); forward и dQ не меняются.

Проверено и не дало выигрыша: размеры чанка KL 4096/8192, параметры ядра FlexAttention
(max-autotune выбирает те же конфиги, что и по умолчанию), `ROWS_GUARANTEED_SAFE` (даёт NaN).
Micro-batch 8 быстрее на 2.5% при пике 72 ГБ. Цель CE вместо KL (как в официальном коде)
была бы быстрее лишь на 8%.

## Структура

```text
orthrus/
  modeling_orthrus.py  модель (самодостаточна: кладётся в экспорт как modeling_orthrus.py)
  objective.py         якоря, маска супервизии, проход диффузии, слитая KL
  train.py             цикл обучения: продолжение, бюджет времени, SIGTERM, оценка, экспорт
  data.py              упаковка сгенерированных диалогов в строки
  datagen.py           выборка промптов и генерация ответов через vLLM
  evaluate.py          метрики скорости, бенчмарки
  checkpoint.py        загрузка модели, чекпоинты, экспорт
  storage.py           HF Storage Bucket
  tracking.py          Trackio, JSONL, прогресс DataSphere, паспорт запуска
  config.py            конфигурация
configs/   эксперименты (qwen3-0.6b.yaml — рецепт статьи, smoke.yaml — быстрая проверка)
jobs/      задания DataSphere
scripts/   ds.py (запуск заданий), lock.py (зависимости), пробы окружения
tests/     тесты на CPU с крошечной моделью (pytest)
```
